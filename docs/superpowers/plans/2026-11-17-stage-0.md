# Этап 0 — план аудита и проектирования

> **Для исполнителей:** выполняйте задачи по порядку. Ставьте отметки после каждого проверяемого результата.

**Цель:** зафиксировать проверенную архитектурную основу и проектную документацию, не начиная продуктовую реализацию.

**Архитектура:** один Cloudflare Worker отдаёт статические файлы Mini App и обслуживает API/webhook. React + Vite + TypeScript составляют будущий frontend; Hono и D1 — будущие API и хранение.

**Стек:** TypeScript, React, Vite, Cloudflare Workers, Hono, D1; только документирование на этом этапе.

**Спецификация:** `docs/superpowers/specs/2026-11-17-stage-0-design.md`; исходные требования: `telegram_ai_mini_app_prompt.md.txt`, разделы 2.1–2.3 и 12, Этап 0.

## Общие ограничения

- «Используй TypeScript как основной язык во всём проекте.»
- «Не удаляй существующие файлы и не переписывай проект без необходимости.»
- «Не выдумывай их.» Значения неизвестных доступов, доменов, Telegram-бота и канала не заполнять.
- «Никогда не записывай реальные значения в `.env.example`, `wrangler.toml`, frontend или Git.»
- Не добавлять продуктовый код, зависимости, инфраструктуру, миграции, CI/CD или деплой: это следующие этапы.
- Не заявлять, что сборка проверена: приложения и manifest-файлов в репозитории нет.
- После проверки сделать обычный commit и push в `origin/main`; не переписывать удалённую историю.

## Риски для проверки

1. Секретоподобные строки могли попасть в новую документацию или пример окружения. Проверить форматами токенов и ключей, затем вручную проверить новые файлы.
2. Пустые значения могут выглядеть как готовая конфигурация. Проверить, что `.env.example` содержит только пустые присваивания, а `ENVIRONMENT.md` помечает список как предварительный.
3. Описание Telegram может обещать недоступную историю. Проверить, что `ARCHITECTURE.md` и `SECURITY.md` ограничивают доступ выданными правами и доступными после подключения данными.
4. Документы могут противоречить выбранной схеме деплоя. Сверить архитектуру, deployment-инструкцию и roadmap на один Worker и отсутствие второго механизма деплоя.
5. Этап 0 может незаметно перейти к реализации. Проверить список изменённых путей: только документы, `.gitignore` и `.env.example`.

- Создать: `TASKS.md`
- Создать: `CHANGELOG.md`

**Интерфейсы:**
- Использовать решения и границы из спецификации Этапа 0.
- Документы должны ссылаться на согласованные имена и одинаково описывать один Worker, React/Vite и D1.

- [ ] Проверить в каждом документе, что неизвестные значения обозначены как неизвестные, а будущая работа не описана как уже выполненная.
- [ ] Записать архитектуру, дизайн-основу, этапы и текущие задачи без неподтверждённых продуктовых деталей.
- [ ] Проверить перекрёстные ссылки и согласованность статусов между `AGENTS.md`, `ARCHITECTURE.md`, `ROADMAP.md` и `TASKS.md`.

### Задача 2: Зафиксировать безопасность, API и локальную конфигурацию

**Файлы:**
- Создать: `ENVIRONMENT.md`
- Создать: `DEPLOYMENT.md`
- Создать: `SECURITY.md`
- Создать: `API.md`
- Создать: `.gitignore`
- Создать: `.env.example`

**Интерфейсы:**
- `ENVIRONMENT.md` описывает назначение будущих переменных и безопасную настройку; реальные значения запрещены.
- `DEPLOYMENT.md` отделяет проверенные сведения от действий, требующих Cloudflare/GitHub/Telegram доступа.
- `API.md` описывает только запланированные границы API и помечает endpoints как не реализованные.
- `.env.example` содержит пустые значения; `.gitignore` разрешает этот файл и исключает реальные `.env` и локальные секреты.

- [ ] Описать безопасность Telegram `initData`, webhook secret, изоляцию пользовательских данных, роли, приватность логов и секреты как требования, не как реализованные меры.
- [ ] Зафиксировать Telegram Business ограничения: только доступные после подключения обновления и выданные права; полная старая история недоступна по обещанию.
- [ ] Описать будущие переменные только как предварительные имена; оставить значения пустыми и отметить неизвестные ресурсы.
- [ ] Добавить игнорирование `.env`, локальных bindings/секретов, зависимостей и генерируемых артефактов; явно не игнорировать `.env.example`.

### Задача 3: Проверить комплект, зафиксировать и отправить

**Файлы:** весь набор из задач 1–2 и два сопровождающих файла дизайна/плана.

**Проверки:**
- Проверить наличие всех файлов: `test -f` для каждого пути из спецификации и обеих записей в `docs/superpowers/`.
- Проверить формат: `git diff --check`.
- Проверить, что значения в `.env.example` пусты; все внешние секреты исключены из индекса.
- Проверить новые файлы на распространённые форматы токенов, приватных ключей и присваиваний секретов.
- Проверить diff и перечень путей: не принимать исходники приложения, зависимости, конфиги деплоя или не относящиеся к Этапу 0 файлы.
- Проверить статусы Git, создать commit с сообщением `docs: complete stage 0 audit`, отправить `main` в `origin` и проверить результат push.

## Самопроверка плана

- Покрывает аудит и все десять документов, перечисленных в мастер-промпте, `.gitignore` и `.env.example`.
- Проверки сборки не добавлены: в репозитории нет приложения для сборки.
- Проверки рисков указаны в третьей задаче и проверках задач 1–2.
- Все действия ограничены Этапом 0; развертывание и реализация остаются вне объёма.
