# Дизайн Этапа 1: инфраструктурный каркас

## Цель

Подготовить первый проверяемый каркас Ecstasy: React Mini App и API в одном Cloudflare Worker, локальную D1 и GitHub Actions. Не имитировать Telegram-подключение и не публиковать приложение без безопасной авторизации Cloudflare.

## Текущее состояние

Этап 0 закоммичен в `main`. Исходников, package manifest, миграций, CI и Cloudflare-конфигурации ещё нет. В репозитории уже определён один Worker, Vite/React/TypeScript, Hono и D1.

Переданные в чат credentials запрещено повторно использовать согласно `AGENTS.md`; они раскрыты. В локальном окружении нет подтверждённых безопасных Cloudflare credentials, Telegram bot token, username и настроек канала. Поэтому можно создать и проверить локальный каркас, но нельзя создать Cloudflare ресурсы, зарегистрировать webhook или пройти живой Telegram flow.

## Подходы

1. **Cloudflare Pages + отдельный Worker API.** Не выбран: два deployable и лишняя координация.
2. **Один Worker с Vite static assets и API — выбран.** Одна архитектура деплоя; официальный Cloudflare Vite plugin поддерживает React SPA и Worker API.
3. **Только статический Mini App.** Не выбран: не даёт целевого места для API, health check и будущего webhook.

Для CI выбран GitHub Actions, поскольку репозиторий уже размещён на GitHub. Автоматический production deploy не включается до появления безопасного Cloudflare token и account ID. Не добавлять второй механизм публикации.

## Объём

- TypeScript, React, Vite и официальный Cloudflare Vite plugin.
- Один Worker с минимальной SPA и `GET /api/health`; никакой фиктивной авторизации или Telegram-сессии.
- D1 binding, первая миграция минимальной таблицы пользователей и локальная проверка миграции. Production database ID задаётся только после создания настоящей D1.
- GitHub Actions для install, typecheck, tests и build. Отдельный deploy workflow допустим только после настройки секретов и безопасной авторизации.
- Документация о командах, bindings, результатах проверок и явных блокерах.

Это локальная подфаза Этапа 1, а не завершение всего Этапа 1. Критерии мастер-промпта включают реальные Cloudflare ресурсы, Telegram `/start`, проверку канала, webhook и опубликованный Mini App. Пока эти пункты заблокированы, Этап 1 остаётся незавершённым; к Этапу 2 не переходить.

## Вне объёма

Telegram bot handlers, `/start`, проверка подписки, webhook registration и публичный деплой требуют Telegram bot token, channel ID/URL и безопасной Cloudflare авторизации. Их нельзя подменять mock-ответами или пустыми значениями, выдаваемыми за настроенную интеграцию. AI, пользовательские API, Telegram Business, UI-разделы и R2 остаются следующими этапами.

## Условия приёмки локальной части

- Чистая установка зависимостей выполняется по lock-файлу.
- TypeScript, unit test, Vite build и локальный Worker smoke test проходят.
- Локальная D1 принимает миграцию.
- `/api/health` отражает реальный статус локального Worker/D1 и не содержит секретов.
- Mini App не показывает вымышленные данные и явно не заявляет о подключении Telegram.
- CI workflow проверяет push и pull request без доступа к секретам.
- Рабочее дерево не содержит credentials; `git diff --check` и secret scan проходят.
- Документы различают локально проверенный каркас и пока не созданные Cloudflare/Telegram ресурсы.

## Условия завершения всего Этапа 1

Дополнительно требуются Cloudflare Worker и D1, настроенный выбранный CI/CD, домен/URL при необходимости, Telegram webhook, рабочий `/start`, фактическая проверка подписки и открытие опубликованного пустого Mini App. Без безопасной авторизации Cloudflare и Telegram credentials эти проверки нельзя выполнить; статус всего этапа остаётся «частично выполнен, заблокирован».

## Открытые блокеры публикации

Нужны безопасная Cloudflare авторизация, настоящие D1 database ID и Workers account configuration, а также Telegram bot token, имя бота, channel ID/URL и права бота в канале. Не считывать и не повторно использовать секреты из переписки.
