# 1. Роль и общая задача

Ты — автономный senior full-stack engineer, software architect, UI/UX designer и DevOps-инженер.

Создай SaaS-продукт в формате **Telegram Bot + Telegram Mini App**, в котором пользователь:

1. Находит Telegram-бота и нажимает `/start`.
2. Сначала видит предложение подписаться на обязательный Telegram-канал.
3. После проверки подписки получает кнопку открытия Mini App.
4. В Mini App настраивает AI-агента, который отвечает людям от имени пользователя через подключённый Telegram Business-аккаунт.
5. Просматривает доступные системе диалоги и историю сообщений, которые поступили после подключения и разрешения доступа.
6. Управляет стилем общения, базой знаний, моделью и настройками агента.
7. Видит фактическую статистику использования и баланс.

Владелец сервиса (создатель проекта) дополнительно получает закрытую админ-панель для управления AI-провайдерами, API-ключами, моделями, резервными провайдерами и общей статистикой.

**Визуальный ориентир:** приложенное изображение — дизайн-референс. Создай минималистичный premium SaaS, не копируй его буквально.

## 2.3. Git — обязательная дисциплина

Моя рабочая сессия может неожиданно завершиться. Поэтому:

- Не делай force push и не перезаписывай чужие изменения.
- Если push невозможен, сохрани локальный commit и сообщи точную причину. Не утверждай, что push выполнен, если это не так.
- После каждого этапа обновляй `ROADMAP.md` и `TASKS.md`, затем commit и push.

- Не добавляй новые продуктовые функции самостоятельно. Сначала предложи их владельцу и дождись согласования.
- Не выполняй опасные действия с реальными пользователями и сообщениями без проверки прав и тестирования.

# 4. Telegram: обязательные технические ограничения

Не путай обычного Telegram-бота с Telegram Business.

Обычный Bot API не даёт боту доступ ко всем личным перепискам пользователя. Для сценария, где AI отвечает от имени личного аккаунта, используй **Telegram Business и подключение Business-бота** с разрешениями, которые пользователь выдаёт сам.

Реализуй предусмотренную Telegram модель Business Connection:
- обработку `business_connection`;
- обработку доступных `business_message` и `edited_business_message`;
- отправку сообщений в разрешённые чаты с использованием соответствующего `business_connection_id`;
- проверку статуса подключения и выданных прав;
- корректную обработку отключения и отзыва доступа.

Не заявляй, что приложение видит все старые чаты и всю историю аккаунта. Показывай только диалоги и сообщения, которые реально доступны через Telegram API после подключения. Не выдумывай отсутствующую историю.

Пользователь должен понимать, какие чаты разрешены для обработки. Не обходи ограничения Telegram и не получай пользовательскую сессию через неофициальную авторизацию по номеру телефона.

**До реализации проверь актуальную официальную документацию Telegram Bot API и Telegram Business.** Если действие не поддерживается API, зафиксируй это и предложи владельцу допустимый вариант.

# 5. Пользовательский путь

## 5.1. Запуск бота

1. Пользователь открывает бота и нажимает `/start`.
2. Backend проверяет подписку на обязательный канал.
3. Если подписки нет, бот показывает приветствие, кнопку «Подписаться на канал» и кнопку «Проверить подписку».
4. Проверяй подписку через Telegram Bot API `getChatMember`. Бот должен иметь необходимые права в канале.
5. После подтверждения подписки показывай кнопку открытия Mini App.
6. Повторный запуск не сбрасывает настройки пользователя.

ID и URL канала задаются конфигурацией, а не хардкодятся в бизнес-логике. Если канал не настроен, в dev-режиме явно сообщай об этом; production-поведение определяется настройкой владельца.

## 5.2. Первый вход в Mini App

Покажи onboarding:
- приветствие и короткое объяснение;
- статус Telegram Business connection;
- действие для подключения Business-бота и выдачи разрешений;
- переход к настройке AI-агента.

Не показывай выдуманный статус «Подключено»: состояние приходит с backend.

## 5.3. Навигация

Основные разделы:
1. **Чаты** — диалоги, сообщения и контроль AI.
2. **Агент** — промпты, база знаний и модель.
3. **Профиль** — баланс, статистика, настройки аккаунта.
4. **Админ-панель** — только владелец сервиса.

На мобильном выбери удобную нижнюю навигацию; на широком экране — компактную боковую навигацию. Не дублируй навигацию без необходимости.

# 6. Функциональные требования

## 6.1. Раздел «Чаты»

Реализуй:
- список доступных диалогов;
- имя собеседника и аватар, если доступны;
- последнее сообщение и время;
- достоверный индикатор непрочитанного, только если его можно определить;
- статус AI для диалога: активен/пауза/требуется внимание — только если эти состояния реально поддерживаются;
- поиск;
- открытие переписки и хронологическую историю;
- различение входящих и исходящих сообщений;
- обозначение AI-ответов, если авторство известно;
- паузу и возобновление AI для конкретного диалога;
- ручную отправку сообщения от имени подключённого Business-аккаунта, если API и права позволяют.

Не добавляй диалоги до появления реальных доступных данных. При пустом списке покажи объяснение, что нужно подключить Telegram Business и дождаться доступных сообщений.

При новом сообщении диалог появляется автоматически. Для MVP используй простой polling с разумным интервалом либо другой совместимый механизм; не усложняй инфраструктуру без причины.

AI не должен отвечать дважды на одно входящее сообщение. Реализуй идемпотентность по Telegram update/message ID и защиту от повторных webhook-событий.

## 6.2. Раздел «Агент» — две страницы

### Страница A — «Промпт»

Это настройка того, **как** AI общается.
- Несколько готовых шаблонов.
- Пользователь выбирает один шаблон.
- Пользователь может создать и сохранить **один собственный промпт**.
- Может редактировать собственный промпт.
- Видит, какой промпт активен.

Примеры шаблонов: дружелюбный, деловой, краткий, неформальный, поддержка клиентов. Содержание и названия можно предложить, но продуктовые формулировки согласовать с владельцем.

Промпт пользователя не может отменять системные ограничения безопасности, права пользователя и правила Telegram.

### Страница B — «База знаний»

Это информация, которую AI использует для понимания пользователя и контекста общения.

Пользователь редактирует один общий документ — логически `knowledge.md`. В него можно внести:
- информацию о себе и предпочитаемое обращение;
- возраст — только если пользователь сам хочет указать;
- сферу деятельности;
- сведения о бизнесе;
- товары, услуги, цены и условия;
- правила общения с клиентами;
- часто задаваемые вопросы;
- важные факты и ограничения.

Возможности: редактирование, сохранение, загрузка `.md`/`.txt` (если реализовано безопасно), экспорт и дата последнего сохранения.

**Два самостоятельных документа пользователя:**
1. `prompt.md` — как AI должен общаться.
2. `knowledge.md` — что AI должен знать о пользователе.

Не смешивай их. Перед запросом к модели backend получает активный промпт и базу знаний пользователя и формирует контекст. Физически хранить отдельные файлы на сервере для каждого пользователя необязательно: допустимы отдельные записи D1 с версионированием.

Ограничь размер документов. Защищайся от prompt injection: содержимое базы знаний — данные, а не доверенные системные инструкции.

## 6.3. Выбор AI-модели пользователем

- Пользователь видит только модели, разрешённые владельцем.
- Может выбрать одну модель; выбор сохраняется.
- Список моделей приходит с backend, не хардкодится во frontend.
- При недоступности модели backend использует разрешённый fallback и корректно сообщает об этом.
- API-ключи и внутренние настройки провайдеров пользователю не показываются.

## 6.4. Профиль пользователя

Покажи, если данные доступны:
- Telegram-имя и username;
- дату регистрации;
- состояние Telegram Business connection;
- выбранную AI-модель;
- баланс;
- фактическое количество AI-сообщений;
- фактическое количество использованных токенов;
- историю расходов/операций, если реализована.

Telegram ID необязательно показывать.

### Баланс и пополнение

Предусмотри внутренний баланс, журнал начислений/списаний, списание за фактическое использование AI и защиту от двойного списания.

Не подключай выдуманную платёжную систему и не имитируй успешное пополнение. До выбора владельцем платёжного провайдера показывай «Пополнение пока не подключено» или скрывай действие пополнения.

## 6.5. Статистика пользователя

Показывай реальные данные:
- отправленные AI-сообщения;
- использованные токены;
- расходы/списания;
- день, неделю, месяц и всё время — если данные достоверно собираются.

Если провайдер не вернул token usage, не выдумывай число. Скрывай метрику или помечай как недоступную.

# 7. Закрытая админ-панель владельца

Владелец сервиса получает отдельную вкладку **«Админ-панель»** внутри Mini App. Обычные пользователи не должны видеть её в навигации и не должны иметь возможность открыть admin API прямым запросом.

## 7.1. Безопасное назначение владельца

**Нельзя просто считать первого пользователя, открывшего публичного бота, владельцем:** это создаёт риск захвата админ-доступа.

Предпочтительный вариант — `OWNER_TELEGRAM_ID` в секретах/переменных окружения. Если владелец не знает свой Telegram ID, предусмотрен одноразовый защищённый bootstrap-код, который задаётся до запуска. Первое назначение должно быть атомарным; после него bootstrap закрывается.

Нельзя повторно назначить владельца через обычный `/start`. Роль и права проверяются backend на каждом admin endpoint.

## 7.2. Управление AI-провайдерами

Только владелец может:
- добавлять несколько AI-провайдеров;
- задавать название и Base URL;
- добавлять API Key;
- включать/отключать провайдера;
- проверять соединение;
- задавать приоритет и резервного провайдера;
- заменять/удалять ключ;
- видеть статус, но не полный сохранённый ключ.

Поддержи OpenAI-compatible API как универсальный адаптер, если провайдеры владельца совместимы. Для несовместимых API предусмотрены отдельные адаптеры. Архитектура расширяемая.

API-ключи хранятся только на сервере, не возвращаются frontend, не попадают в Git и логи. UI получает только маскированное состояние. Для динамически управляемых ключей спроектируй безопасное хранение/шифрование с ключом шифрования в Cloudflare Secret; не изобретай собственную криптографию. Опиши ротацию ключей.

## 7.3. Управление моделями

Владелец может добавлять несколько моделей от разных провайдеров и задавать:
- provider;
- model ID;
- отображаемое название;
- статус доступности;
- приоритет;
- доступность для пользователей;
- возможность использовать как fallback.

Пользователи видят только активные и разрешённые модели.

## 7.4. Автоматическое переключение провайдеров

Реализуй контролируемый fallback:
1. Backend выбирает доступный provider/model по приоритету.
2. Выполняет запрос.
3. При временной ошибке, недоступности или исчерпании квоты переключается на следующий совместимый вариант.
4. Фиксирует фактического провайдера, модель, usage и результат.
5. Не повторяет запрос бесконечно.
6. Не переключается при пользовательских ошибках, которые другой провайдер не исправит.
7. Учитывает таймауты и лимит попыток.
8. Не списывает с пользователя дважды за один запрос.

Не утверждай, что можно узнать баланс любого внешнего API-провайдера. Если API не предоставляет баланс, используй ошибки провайдера и ручное отключение владельцем.

## 7.5. Общая статистика сервиса

# 9. Архитектура данных

Спроектируй нормализованную D1-схему и миграции. Минимальные сущности:

- `users` — Telegram user ID, профиль, дата регистрации, роль, настройки.
- `business_connections` — состояние Business Connection и разрешения.
- `dialogs` — доступные диалоги, chat ID, собеседник, последнее сообщение, состояние AI.
- `messages` — Telegram message ID, направление, текст/тип, время, источник отправки.
- `processed_updates` — идемпотентность webhook updates.
- `agent_settings` — активный prompt, выбранная модель, параметры поведения.
- `user_documents` — документы prompt/knowledge, версии и дата обновления; либо отдельные таблицы.
- `providers` — конфигурация провайдеров без открытого хранения ключей.
- `models` — модели и доступность.
- `usage_events` — токены, provider, model, статус, время, пользователь, запрос.
- `ledger_entries` — начисления и списания баланса.
- `admin_settings` — настройки сервиса.
- `audit_logs` — важные действия администратора.

Все пользовательские данные изолируй по `user_id`. На backend проверяй принадлежность каждого диалога пользователю при каждом запросе.

# 10. AI pipeline — как агент отвечает

Раздели обработку на понятные шаги:

1. Получить Telegram webhook.
2. Проверить секрет webhook, если настроен.
3. Зарегистрировать update для защиты от повторной обработки.
4. Определить владельца Business Connection.
5. Проверить подключение и выданные права.
6. Проверить, что диалог разрешён для AI и не на паузе.
7. Получить актуальный `prompt.md` пользователя.
8. Получить актуальный `knowledge.md` пользователя.
9. Получить выбранную модель и разрешённого провайдера.
10. Собрать контекст с безопасным разделением системных инструкций и недоверенных данных.
11. Отправить запрос AI provider.
12. Проверить ответ и допустимую длину.
13. Отправить ответ через Telegram Business API от имени подключённого аккаунта, если права и API это позволяют.
14. Сохранить входящее и исходящее сообщения.
15. Сохранить фактический token usage и provider/model, если данные доступны.
16. Обновить диалог и статистику.
17. Обработать ошибки без дублирующих ответов.

Добавь таймауты, ограничение повторов, обработку rate limits, безопасные логи, возможность выключить AI глобально/для пользователя/диалога и защиту от параллельной обработки одного update.

Не отвечай автоматически на сообщения вне разрешённой области доступа. Сначала реализуй безопасное поведение и тесты.

# 11. Безопасность и приватность

Обязательно:
- Валидировать Telegram Mini App `initData` на backend по официальному алгоритму Telegram. Не доверять `user` с frontend без проверки подписи и `auth_date`.
- Проверять срок актуальности `auth_date`.
- Не считать Telegram ID, переданный клиентом, доказательством личности.
- Проверять владельца каждого ресурса на сервере.
- Проверять роль владельца для каждого admin API.
- Защищать webhook `secret_token`, если используется.
- Не хранить bot token и AI API keys в Git.
- Не отправлять секреты в браузер и не писать их в логи.
- Не писать полное содержимое личных переписок в обычные логи.
- Не использовать общий API-ключ в клиентском коде.
- Защитить от повторных webhook и двойного списания.
- Ограничить размер промпта и базы знаний.
- Безопасно обрабатывать файлы.
- Добавить базовую защиту от спама и чрезмерного числа запросов.
- Учитывать удаление/отзыв Business Connection.
- Предусмотреть удаление пользовательских данных и отключение AI.

Проведи проверку зависимостей и базовые security-тесты.

# 16. Продуктовые решения, которые нельзя менять без согласования

1. Это Telegram Mini App, а не отдельный мобильный сайт, который притворяется Telegram.
2. AI общается от имени пользователя через поддерживаемое Telegram Business-подключение.
3. Mini App показывает реальные доступные диалоги и сообщения.
4. У пользователя два документа: промпт поведения и база знаний.
5. Пользователь выбирает готовый промпт или создаёт один собственный.
6. Пользователь выбирает модель из списка, который контролирует владелец.
7. Владелец может добавлять несколько AI-провайдеров и моделей.
8. При проблеме с основным провайдером работает контролируемая резервная схема.
9. Админ-панель доступна только владельцу и защищена на backend.
10. Пользовательские и общие метрики строятся только на фактических данных.
11. Дизайн — минималистичный тёмный SaaS по приложенному референсу, без градиентов и лишнего декора.
12. Сначала выпускай небольшие рабочие этапы, а не огромный недоделанный релиз.
13. После каждого логического этапа — commit и push.
14. Новые функции сначала предлагай владельцу, не внедряй самовольно.
